# EasyLens 首轮验证方向（调研草稿）

日期：2026-10-26。状态：调研假设，不作为技术选型结论。本机受控样本的小实验见 [本地取像与 OCR 结果](2026-10-26-local-lens-probe-results.md)；尚未进行真实产品的端到端实测。

## 一句话判断

用户提出的三个关键点成立，但最早要验证的不是单个 OCR 或模型 API 的速度，而是**遮罩窗口覆盖目标时，能否稳定、准确地取得窗口下方的画面，并在目标改变后只展示对应结果**。建议先做“移动瞄准 → 短暂停稳 → 锁定一次画面 → 本地 OCR 和英文门禁 → 云端文字翻译”的闭环。移动时窗口保持流畅，不要求每一帧都跑 OCR 或调用模型。

当前机器为 macOS 15.7.7、Intel Core i7-8569U、x86_64；社区中的 Apple Silicon 数据不能直接代替本机结果。

## 对三个判断的补充

### 1. OCR 必须快，但应拆开“取像”和“识别”

屏幕画面获取、裁剪、OCR、语言判断分别计时。macOS [ScreenCaptureKit 示例](https://developer.apple.com/documentation/screencapturekit/capturing-screen-content-in-macos)提供按显示器或窗口捕获、排除本应用窗口、持续获取帧和更新捕获配置的能力；[sourceRect](https://developer.apple.com/documentation/screencapturekit/scstreamconfiguration/sourcerect)可限制显示器捕获区域。Apple [Vision 文档](https://developer.apple.com/documentation/vision/vnrecognizetextrequest)提供文字识别请求与 `.fast` / `.accurate` 两种模式，[实时识别示例](https://developer.apple.com/documentation/vision/extracting-phone-numbers-from-text-in-images)把快速模式、小区域和关闭语言纠错组合使用。它们证明有可实验的 API 路径，不证明 EasyLens 在本机达到任何延迟目标。

优先验证遮罩自身是否进入截图、排除自身后是否能看到真正的底层内容，以及多显示器、Retina 缩放、滚动页面和其他悬浮窗的行为。这里失败，即使 OCR 很快也无法形成正确产品。社区开源应用 [Lenscap](https://github.com/rutmehta/Lenscap)已经把区域截屏、Vision OCR、悬浮界面和自身窗口排除组合在同一个 macOS 应用中，可作实现线索；它的 README 没有给出本产品所需的实时延迟保证。

移动期间可以只更新边框与预览；仅在候选区域变化足够小、停稳后做一次 OCR，或按较低频率抽样。对静止且画面未变化的区域复用结果。是否需要“移动中实时标出英文”应单独做用户体验实验，不能把它与翻译闭环绑成首个门槛。

### 2. 云端模型可翻译文字，也可看图；首版宜先测文字路径

截至本次调研，[DeepSeek Vision 文档](https://api-docs.deepseek.com/guides/vision/)列出可接收截图的 `deepseek-flash`，[小米 MiMo 图像理解文档](https://mimo.mi.com/docs/en-US/quick-start/usage-guide/multimodal-understanding/image-understanding)也列出图片 URL 与 Base64 输入。这只说明接口能力，无法推断特定网络、时段和模型的首字延迟、完成时间、识别准确度或价格；这些需要用同一批样本实测。[MiMo Responses API 文档](https://mimo.mi.com/docs/en-US/api/chat/responses)支持流式输出，流式首字可改善等待感，但不会让尚未返回的译文提前完成。

产品约束是非英文内容跳过后续执行。因此“直接把每张截图发给多模态模型”不能作为默认主路径：本地没有英文门禁时，非英文画面也会上传并进入模型处理；混排截图还可能包含不该处理的内容。首版基线应是本地 OCR → 按文字片段判定英文 → **只发送确认后的英文文字** → 英译中。截图直传只作为对照实验，须明确是否允许上传整张区域、如何处理混排及隐私。

“拉丁字母”不等于英文。Apple [Natural Language 语言识别](https://developer.apple.com/documentation/naturallanguage/identifying-the-language-in-text)可返回候选语言；短词、专名、代码、网址与 OCR 错字仍可能难判。先按 OCR 文字行或块做门禁，低置信度时宁可不发；混排粒度和误跳过容忍度需用样本确定。

### 3. 一秒聚焦是合理的交互假设，应把它当作“锁定快照”

建议原型状态为：`跟随移动 → 候选区域停稳 → 聚焦提示 → 锁定快照 → 识别/翻译 → 展示`。一秒是用户可理解的聚焦上限候选值，不应硬编码为所有场景都必须等满一秒；用户也可用点击或第二次快捷键主动锁定。聚焦期间如果位置或底层画面明显变化，就重新计时或提示重新瞄准。

锁定后，翻译绑定这张快照及其区域 ID；用户移动镜头时，旧请求可取消或让其完成但不再投到新区域。展示前核对“结果属于当前快照”，避免慢响应覆盖新目标。社区项目 [screenquest](https://github.com/DanielTea/screenquest)采用本地快速感知、异步慢模型并在动作前重新核对画面；它报告的是特定 Apple Silicon 游戏场景的一次运行，适合借鉴时序设计，不可当作 EasyLens 的性能证明。

## 建议测量的用户路径

| 阶段 | 需要记录的时间与结果 | 首轮判据（待体验验证的目标，不是现有性能） |
| --- | --- | --- |
| 唤起、拖动 | 快捷键到窗口可见；拖动丢帧与输入响应 | 移动始终顺畅，OCR 不阻塞窗口线程 |
| 停稳、取像 | 位置稳定到取得正确底层像素；遮罩是否污染图像 | 一秒聚焦内能锁定正确快照 |
| 本地 OCR、英文门禁 | 取像到文字与语言决定的 p50/p95/p99；漏识别、误判 | p95 争取低于 500 ms；纯非英文不发模型 |
| 云端翻译 | 请求到首个可显示译文、完整译文的 p50/p95/p99；超时与失败率 | 首字约 1–2 秒、完整约 3 秒作为待验证体验目标 |
| 目标变更 | 旧请求返回后是否污染新目标；重复请求次数 | 错位显示为零；相同快照尽量不重复请求 |

上述数值只是明确何时调整交互或否定方案的初始假设。尤其要分别报告冷启动与预热、纯英文与混排、不同字号与背景、静态与滚动内容、本机硬件与网络条件；不要只报平均值或单次最快结果。整体体感时间可拆成 `停稳等待 + 取像 + OCR + 语言门禁 + 网络往返 + 生成 + 展示`，各段的尾延迟比宣传的模型速度更重要。

## 最小实验顺序

1. **捕获实验**：在 `tmp/scripts/` 建最小 macOS 脚本/原型，取得指定矩形图像；验证悬浮遮罩排除、底层像素、权限和坐标。先使用静态英文页面，不接模型。
2. **OCR 实验**：同一批区域图比较 Vision `.fast` / `.accurate`，记录逐段耗时、识别误差和英文门禁误判；覆盖空白、纯中文、法德文、代码、混排、小字和低对比度。
3. **移动与锁定实验**：模拟连续拖动、停稳、重新移动和页面滚动；验证一秒聚焦交互、重复识别频率、旧结果隔离及 CPU/内存占用。
4. **云端对照实验**：在用户提供测试密钥和可上传样本后，以相同内容比较“英文 OCR 文本翻译”与“区域截图直传”的首字、完成时间、质量和成本。先测一个模型即可；换模型前确认是否是网络或提示词瓶颈。
5. **端到端判断**：在真实桌面应用上走完整路径，再决定是否需要持续 OCR、是否采用截图直传以及正式客户端技术栈。

## 尚待确认的产品规则

- “非英文直接跳过”是整张区域跳过，还是混排时仅跳过非英文行/块？草稿暂按后者设计实验。
- 镜头移动后，原译文是保留在历史中、立即消失，还是附着在锁定的快照上？
- 首发是否仅验证 macOS？当前机器适合先做 macOS 可行性实验，但不能由此推出最终平台范围。
- 截图是否允许发送云端、允许保存多久？文字发送与图片发送应分别定义。
